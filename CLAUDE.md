# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A set of Win32/C++20 UI libraries built on WTL. Native Windows only: MSVC, Unicode, Visual Studio solution `WTLHelper.sln`. This directory is a git submodule of the parent `WinSysLive` repo (`../`), and the parent `WinSysLive.sln` builds `WTLHelper` and `GraphControl` directly. Changes to those two projects affect the parent app.

## Build

There is no CMake or lint setup; everything goes through MSBuild. Most projects use toolset v145, which ships with VS 18 (`C:\Program Files\Microsoft Visual Studio\18\Enterprise\MSBuild\Current\Bin\MSBuild.exe`). The BasicDemo and HexTest projects still use v143.

```powershell
# whole solution (configs: Debug/Release; platforms: x64, x86, ARM64)
msbuild WTLHelper.sln /p:Configuration=Debug /p:Platform=x64 /m
# a single project
msbuild WTLHelper\WTLHelper.vcxproj /p:Configuration=Debug /p:Platform=x64
```

Every project uses the static C runtime (`/MT`, `/MTd`) in every configuration; a library on the DLL runtime fails to link (LNK2038) with the others.

NuGet dependencies (`packages.config`): Detours (`ThemeHelper.cpp` includes `<detours/detours.h>`), WIL and the `wtl` package. Restore them before building (`nuget restore WTLHelper.sln`). The WTL headers are also vendored in `WTL/`, which `WTLHelper` and `HexControl` add to their include path.

## Tests

The automated tests are in `GraphControlTests/tests.cpp`, `WTLDockTests/`, `PropertyGridTests/tests.cpp`, `LogViewTests/tests.cpp`, `ColorPickerTests/tests.cpp`, `AccordionTests/tests.cpp`, `DiffViewTests/tests.cpp`, `CommandPaletteTests/tests.cpp`, `RibbonBarTests/tests.cpp`, `BreadcrumbTests/tests.cpp`, `NotifyTests/tests.cpp` and `GanttTests/tests.cpp`. Each is a console exe with a hand-rolled harness and no framework. The process exit code is the number of failed checks.

- Add a test with `TEST(Name) { CHECK(...); }`, then add a `Run_Name();` call in `wmain`. Registration is manual, so a test you don't call never runs.
- To run a single test, comment out the other `Run_*` calls in `wmain`. There is no filter argument.
- The tests mostly cover pure data models (`GraphData` and the cell graphs, the dock layout, the property grid's item tree and formatters, the log view's line storage, the color picker's conversions and pixels, the accordion's layout and state, the diff view's diff, rows and selection text, the command palette's matching and search, the ribbon's shrinking, layout, key tips and state, the breadcrumb's layout, folding, history and path text, the notifications' link markup, wrapping, layouts, toast placement and timer, the Gantt chart's dates, calendar, time scale, task tree, links, scheduling, bar geometry, dragging and undo); `WTLDockTests/ui_tests.cpp` also creates windows. Anything else that needs an HWND or a render target is checked by hand with the demo apps (`GraphDemo`, `CellGraphsDemo`, `NodeGraphDemo`, `TreeListViewDemo`, `PropertyGridDemo`, `LogViewDemo`, `ColorPickerDemo`, `AccordionDemo`, `DiffViewDemo`, `CommandPaletteDemo`, `RibbonBarDemo`, `BreadcrumbDemo`, `NotifyDemo`, `GanttDemo`, `HexTest`, `BasicDemo`).

## Architecture

The solution has two families of projects.

**1. `WTLHelper/`: the main static library** (precompiled header `pch.h`, which defines `NOMINMAX` and pulls in ATL/WTL and the STL). It has two independent theming systems:

- **Dark mode (current path)**: `WTLHelper` (`WTLHelper.h/.cpp`) wraps the vendored **darkmodelib** in `WTLHelper/DarkMode/` (third-party, MPL-2.0, derived from Notepad++). Call `WTLHelper::InitDarkMode()` / `SwitchToMode()`. The theming hook is per thread: `InitDarkMode` installs it for its thread, and another UI thread calls `WTLHelper::InitThread()` (and `TermThread()` before it ends) for its windows to be themed too; `SuspendHook`/`ResumeHook` affect only the calling thread. Mode changes are broadcast with the registered `WTLHelper::ThemeChangedMessage`. `ApplyMode` also gives every list view the mode's own theme name (`DarkMode_Explorer` or `Explorer`): darkmodelib sets `Explorer` in both modes, and a list view that already had it kept the old mode's theme data, so a selected item stayed light (black text) after switching to dark. `WTLHelper.cpp` also Detours-hooks `GetSysColor`/`GetSysColorBrush` so stock controls pick up dark colors. The `ColorTone` enum mirrors `DarkMode::ColorTone` and must stay in sync, because the code `static_cast`s between them. Avoid modifying the `DarkMode/` files themselves unless necessary; they come from upstream. One local change must survive an update from upstream: in `DmlibSubclassControl.cpp` the control subclasses pass `WM_DPICHANGED_AFTERPARENT` on (`DefSubclassProc`) after their own handling instead of returning 0. Upstream swallows it, and since dark mode subclasses a control after the app does (when the mode is applied), the app's own subclasses (`ListViewHelper::EnableColumnDpiScaling`, a filter box resizing itself) never got it; `DpiTest` doesn't turn dark mode on, so it can't catch that.
- **Custom themes (`ThemeHelper` + `Theme`)**: `ThemeHelper::Init()` installs a `WH_CALLWNDPROCRET` hook plus Detours hooks on `GetSysColor`/`GetSysColorBrush`/`GetSystemMetrics`. In `HandleCreateWindow` (`ThemeHelper.cpp`), every newly created window is matched by class name and subclassed with the corresponding `Custom*.h` class (`CCustomListView`, `CCustomButtonParent`, `CCustomHeaderParent`, …). Some of those subclass the *parent* window to handle `NM_CUSTOMDRAW`. These objects are heap-allocated and free themselves in `OnFinalMessage`. To theme a new control type, add a `Custom*.h` class and a branch in `HandleCreateWindow`. Use `Suspend()`/`Resume()` around windows that must not be themed.

The rest of `WTLHelper` is a grab bag of standalone helpers: list views (`VirtualListView.h`, `ColumnManager`, `SortHelper`, `SortedFilteredVector.h`), settings persistence (`Settings`, whose `GetPath` is the key or INI file `Save` writes, which `LoadFromKey`/`LoadFromFile` replace; `IniFile` = thin `GetPrivateProfile*` wrapper, `IniDocument` = full in-memory INI parser with typed reads and atomic save via temp file), and `CompoundFile`, `SecurityHelper`, `IconHelper`, `ClipboardHelper`, `StringHelper`, tab-view helpers and others.

**2. Standalone control libraries**: each is a static lib with a public header in `include/`, implementation in `src/`, and usually a matching demo exe. They don't depend on `WTLHelper`.

- `GraphControl`: time-series graph (Direct2D/DirectWrite, namespace `GraphCtrl`). `GraphData` is a separate pure model, which is what the tests target. It also has the cell graphs (`include/CellGraphs.h`, no window): line and column sparklines, meters and stacked bars drawn in list view and TreeListView cells. `DrawSparkline`/`DrawColumns`/`DrawMeter`/`DrawStacked` draw in software over a cell's pixels (copied into a per-thread DIB section and back). `CellHistory<Key>` keeps a `Series` per row and drops the rows a refresh didn't see. The `CellGraphs` helper gives columns a kind and a style, and draws them from the parent's `NM_CUSTOMDRAW`, with the cells' data from a callback. It copies a cell before the list paints it (sub-item pre-paint) and after (sub-item post-paint): the list keeps painting its own selection, hot and background colors, and `Cells::CellBackground` takes the text out before the graph goes on. That works both when a themed list (Explorer, dark mode) draws the row's background first and when a list fills each cell itself (the classic highlight). TreeListView relays the sub-item post-paint stage for this. Colors left at `CLR_DEFAULT` follow the cell's background. A meter can carry text over its bar (`CellData::Text`, drawn with GDI into the same DIB in the list's font, in two colors split where the bar ends). Sparklines and columns can have a dashed reference line, and a sparkline's color can follow thresholds by its newest sample. `EnableTooltips` subclasses the list view (a TreeListView's inner list, with a row-to-item mapping) and moves one tooltip tool to the graph cell under the mouse: the last, lowest, highest and average samples shown (`Cells::Stats`), in the column's `SetFormat` format, or the data's own `Tooltip`. To keep painting cheap, the helper doesn't copy the cell out and back a second time to take the text out: a `Cells::BackgroundScope` hands the before-copy to the renderer, which does it in its own buffer. The probe pixel is taken from the part of the cell the DC can paint (a row cut off at the bottom of the list). Pixels are blended in fixed point, and meter text goes through `ExtTextOutW` (`DrawTextW` only to add an ellipsis); the demo's View > Measure List Painting times a repaint (View > Graphs turns them off to compare). Colors too close to the cell's background are moved apart (`Visible`), and in high contrast every graph uses the system text color that reads on the cell (`Farthest`; `ForceHighContrast` lets the tests choose). The window-free parts (`src/CellGraphsModel.*`: scaling, geometry, the rasterizer, `CellBackground`) are covered by `GraphControlTests`; `CellGraphsDemo` is for checking by hand.
- `NodeGraphControl`: node/edge graph editor (namespace `NodeGraphCtrl`). It notifies the parent via `WM_NOTIFY` `NGCN_*` codes.
- `TreeListView`: tree+columns control registered as window class `WC_TreeListView`, with an opaque `HTLITEM` handle API in the style of common controls.
- `HexControl`: hex editor control (`BufferManager`/`MemoryBuffer`/`Selection`).
- `PropertyGrid`: categorized name/value editor (`CPropertyGridCtrl`, window class `WC_PropertyGrid`), self-drawn with GDI, with a C-style API: `HPRGITEM` handles, `PRGVALUE` tagged values, `PRGN_*` notifications. The `PRG` prefix avoids commctrl's Pager control, which owns `PGN_`/`PGF_`/`PGK_`. The window-free model (`src/PropertyGridModel.*`: the item tree, the rows of each view, formatting) is covered by `PropertyGridTests`; `PropertyGridDemo` is for checking by hand.
- `LogView`: read-only log/text viewer for millions of lines (`CLogViewCtrl`, window class `WC_LogView`), GDI-drawn, `LGV`-prefixed C-style API (`LGVLINE`, `LGVSTYLE`, `LGVN_*` notifications). Lines are kept in chunked storage with an optional limit that drops the oldest, or supplied by the parent in virtual mode (`LGVN_GETDISPINFO`). `AppendLine`/`AppendLines`/`AppendText` may be called from any thread: from other threads lines are queued under a lock and taken in by a posted `WM_LGV_FLUSH`. The text area is a child window (`LgTextWindow`, which owns the scroll bars) whose messages are handled in the control's `ALT_MSG_MAP(1)`. The view works in rows (the lines a filter shows, `LgRowMap`, by serial number so dropped lines just pop off the front), while API positions (`LGVPOS`, line indexes) stay those of all the lines. Filtering and `FindNext` run in slices on a `WM_TIMER` (`LogViewFilter.cpp`, `LogViewSearch.cpp`), not posted messages, which would starve input and painting; color rules are applied at paint time. The optional toolbar (`LogViewToolbar.cpp`: filter and search boxes with their options, level buttons, Follow) is drawn on the control above the text child and drives the same API; the text child exposes MSAA as a list of the rows shown (`LogViewAccessible.cpp`). `LogViewDemo` links WTLHelper on x64 to try its dark mode. The window-free model (`src/LogViewModel.*`) is covered by `LogViewTests`; `LogViewDemo` is for checking by hand.
- `ColorPicker`: color picker (`CColorPickerCtrl`, window class `WC_ColorPicker`), `CPK`-prefixed C-style API (`CPKHSV`, `CPKCOLORS`, `CPKN_COLORCHANGING`/`CPKN_COLORCHANGED`): a saturation/value area, a hue bar and an optional alpha bar (`CPKS_NOALPHA`), plus a panel with the new/original swatch (`CPKS_NOSWATCH`) and H S V A R G B Hex fields (`CPKS_NOFIELDS`). The control is a `WS_EX_CONTROLPARENT` container: the gradients are a child window (`CpGradientWindow`, handled in the control's `ALT_MSG_MAP(1)`) and form one tab stop, and the fields are borderless edits whose frames, labels and spin buttons the control draws (`ColorPickerFields.cpp`), so they follow its colors. Under the fields are swatch rows of 12 (`ColorPickerSwatches.cpp`): the palette, custom slots (`CPKN_CUSTOMCHANGED`) and recent colors added by the app (`CPKS_NOPALETTE`). An eyedropper button beside the swatch picks from the screen. While picking, a temporary `WH_MOUSE_LL` hook follows the mouse (capture doesn't reach other apps' windows without a button held) and swallows the picking click, and a layered, click-through `CpMagnifier` popup shows the pixels. `ColorPickerDialog(CPKDIALOG*)` is a modal `ChooseColor` replacement built from an in-memory dialog template (the library has no resources), with a live-preview callback. `CColorButtonCtrl` (`WC_ColorButton`) is a swatch button that opens a picker popup; it runs its own message loop while open, so Tab, Enter and Escape work through `IsDialogMessage`. Both size the picker with `GetIdealSize()`. Shared GDI helpers and the system colors (including high contrast) are in `src/ColorPickerDraw.h`. The swatches are drawn by a second child window (`CpSwatchWindow`, `ALT_MSG_MAP(2)`) that comes after the fields in the tab order and handles the keys. It returns `HTTRANSPARENT`, so the control still gets the clicks and the tooltips. MSAA (`ColorPickerAccessible.cpp`): each object wraps the system's standard one for its window and passes through whatever it doesn't answer. A wrapper must never take its name from the same window's `OBJID_WINDOW` object, which asks the client object again and recurses until the stack overflows. An app can use `ColorPickerDialog` for PropertyGrid colors by handling `PRGN_BUTTONCLICK`. The color is kept as HSV, so the hue survives gray and black, and `SetColor` with the color it already has changes nothing (`CpUpdateHsv`). It's drawn in software into a DIB section back buffer; the gradients are cached and redrawn only when the hue, the color or the size changes. Like LogView, it follows WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message, with no dependency. The window-free model (`src/ColorPickerModel.*`: conversions, hex, layout, pixel drawing) is covered by `ColorPickerTests`; `ColorPickerDemo` (which links WTLHelper on x64) is for checking by hand.
- `Accordion`: a vertical stack of collapsible sections (`CAccordionCtrl`, window class `WC_Accordion`), `ACD`-prefixed C-style API (`ACDSECTION`, `HACDSECTION` handles, `ACDS_*` styles, `ACDN_*` notifications; not `AC`, which commctrl's animate control owns). Each section is a GDI-drawn header (chevron, optional image-list icon, semibold title, right-aligned info text) over a body that is a window the app gives it, made a child of the control. A body is a fixed height (DIPs), a share of the leftover space by weight (fill), or the height its content asks for (fit, `ACDN_GETFITHEIGHT`, asked again when the width changes or with `UpdateFitHeight`); the control scrolls when the open sections don't fit. `ACDS_SINGLEEXPAND` keeps one section open; `ACDSS_NOCOLLAPSE` sections stay open. Headers can carry buttons (`ACDBUTTON`, `ACDN_BUTTONCLICK` with the button's rect for a drop-down menu; one tooltip tool moved to the hot button). The user opening or closing a section sends `ACDN_EXPANDING` (a non-zero return vetoes) and then `ACDN_EXPANDED` for it and every section that closed with it; the API sends neither. The headers take the keyboard focus through a child window with no size (`AcdFocusWindow`, handled in the control's `ALT_MSG_MAP(1)`), first in the z-order: the dialog manager tabs into a `WS_EX_CONTROLPARENT` container rather than to it. `PositionBodies` keeps the bodies after it in section order, so Tab goes headers, then the bodies top to bottom; the focus in a body that closes goes to its header. Opening and closing animates (150 ms on a timer, off with `ACDS_NOANIMATION` or Windows' client-area animation setting, which `ACDS_ALWAYSANIMATE` overrides): a body opening or closing stays at its full height with a window region showing its part, so its content doesn't reflow every frame. The user can drag a body's bottom edge (`ACDS_NORESIZE` turns it off; the grab band is the top of the header below, as the body window covers its own edge) and drag headers to reorder the sections (`ACDS_NOREORDER`; past `SM_CYDRAG`, with an insertion line and the header's image following the mouse in a layered popup the mouse goes through, so a header toggles on the button's release), and Escape or a lost capture calls a drag off; `ACDN_SECTIONRESIZED` and `ACDN_SECTIONMOVED` follow. A resized edge follows the mouse: a fill section below takes the difference, or else the nearest open section below trades height with it (`AcdResize`). `GetState`/`SetState` save and restore the order, the open sections and the sizes as text (`AcdSaveState`), matching sections by id, which `InsertSection` keeps unique. While an edge is dragged or a section animates, the control turns on `WS_EX_COMPOSITED` (`UpdateComposited`), so the bodies resizing every move or frame are painted with it off screen rather than each erasing on its own, which flickered; only meanwhile, since composited any body's repaint is the whole control's. Since the bodies are its children, the control forwards their `WM_COMMAND`, `WM_NOTIFY`, owner-draw, child scroll bar and `WM_CTLCOLOR*` messages to its parent, except `WM_CTLCOLORSTATIC`, which it answers itself with its background (a parent passing it to `DefWindowProc` would turn read-only edits dialog gray, and there's no telling that answer from a chosen color). Like LogView and ColorPicker, it follows WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message. High contrast uses the system colors even over colors the app set. MSAA (`AccordionAccessible.cpp`) is on the headers' focus window: a group named for the accordion (asked of the accordion's window, never the focus window's own `OBJID_WINDOW`, which would recurse), its children each header (an outline button, expanded or collapsed, described by its info text, Expand/Collapse as its default action, which notifies like the user's click) followed by its buttons (push buttons named by `pszTip`); focus, state, reorder, name and description changes are reported once a client has asked for the object. Ctrl+Up/Down moves the focused section. The window-free model (`src/AccordionModel.*`: the sections' state, the layout of fixed, fill and fit bodies with minimums and scrolling, the animation steps, hit testing, resizing, reordering and the saved state string) is covered by `AccordionTests`; `AccordionDemo` (which links WTLHelper on x64) is for checking by hand.
- `DiffView`: compares two texts line by line (`CDiffViewCtrl`, window class `WC_DiffView`), `DFV`-prefixed C-style API (`DFVPOS`, `DFVCHANGE`, `DFVCOLORS`, `DFVN_*` notifications), side by side or unified (`DFVL_*`), GDI-drawn. The app gives it the two texts and the control diffs them itself (`src/DiffViewModel.*`): Myers' algorithm in linear space (as GNU diff's `diffseq`) between anchors, the lines found once on each side kept in order by a longest increasing subsequence, with a cost limit that splits a range at the furthest point either search reached so unrelated texts stay fast (so a diff can be a little longer than the shortest). Pure inserted or deleted runs are slid to end on a blank line (git's sliding). Ignore case and whitespace (`DFVF_*`) compare normalized lines; a last line with no line break differs from the same line with one. The lines of a change are paired by similarity (a DP, or by position past 64x64), and each pair gets its changed words, or characters when a word mostly stayed. `DfBuildRows` lays out the rows: side by side the unpaired lines of a change share rows and the shorter side is padded (hatched filler), unified a change's left lines then its right ones; runs of unchanged lines fold to `SetContextLines` lines of context, and a fold opens on a click or Enter (`DFVN_FOLDEXPANDED`). `DfDocument` holds the texts, the diff, the rows and a line-to-row map per side. Positions (`DFVPOS`) are a side, a line and a column, so the caret and selection (`DiffViewSelection.cpp`) survive a new diff, folding and switching layouts; side by side a selection stays in its pane, unified it runs over rows. F7/Shift+F7 go between changes, F6 to the other pane. An overview strip beside the scroll bar shows every change and the part in view. `EnableMerge` (`DiffViewMerge.cpp`) puts arrows in the strip between the panes; the user's merge (an arrow, Alt+Right or Alt+Left) sends `DFVN_MERGE` (non-zero stops it) then `DFVN_TEXTCHANGED`; merges are undone with `Undo`/Ctrl+Z, each keeping only the lines it replaced. Texts past `SetBackgroundThreshold` (100,000 lines) are compared on a detached worker thread (`DfJob`, cancelled through `DfOptions::cancel`) that posts `WM_DFV_DIFFDONE`; meanwhile the last diff stays shown with a note and the text queries answer about the new texts (`Latest`), and `DFVN_DIFFDONE` follows. Like LogView, it follows WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message; high contrast uses the system colors even over the app's, framing the changed words instead of shading them (`ForceHighContrast` for testing). MSAA (`DiffViewAccessible.cpp`) is a list of the rows on the control itself, named from the standard proxy (never the window's own `OBJID_WINDOW`, which would recurse); a fold's default action opens it. The model is covered by `DiffViewTests`; `DiffViewDemo` (which links WTLHelper on x64) is for checking by hand.
- `CommandPalette`: a search box over a list of the app's commands (`CCommandPaletteCtrl`, window class `WC_CommandPalette`), `CMDP`-prefixed C-style API (`CMDPITEM`, `CMDPPROVIDER`, `CMDPS_*`, `CMDPN_*`; not `CPL`, Control Panel's; internal names are `Cmp*`, since ColorPicker owns `Cp*`). Commands are added one by one or read from a menu (`AddFromMenu`: names without `&`, the text after a tab as the shortcut, the submenu path as the category, grayed and checked states); `RefreshMenus(window)` reads them again, first sending the window `WM_INITMENUPOPUP` for each submenu as a menu opening would, and keeps each menu's commands in their place. Typing filters by fuzzy matching (`src/CommandPaletteModel.*`, `CmpPattern`): the typed words in any order, each a subsequence of the label ("Category: Name"), scored by a DP that rewards word starts (camel humps and digits too), runs and a capital typed on a capital, and charges gaps; the matched letters are drawn bold in the accent color. Ties go to the recently used (`CmpRecent`, saved as "12;7;301"), which also come first with nothing typed. The box is a real `Edit` subclassed with `CContainedWindowT` (`CContainedWindow::Create` makes an `ATL:Edit` superclass, which the system's edit accessibility and `FindWindowEx("Edit")` don't know); the list is a child window (`CmpListWindow`, `src/CommandPaletteList.h`) with its own scroll bar, handled in `ALT_MSG_MAP(2)`, and the focus stays in the box. Enter or a click sends `CMDPN_EXECUTE` (non-zero: the app ran it), then posts `WM_COMMAND` to the owner. `CCommandPalettePopup` hosts a palette at the top of the owner's client area, sized to its results (`CMDPN_RESULTSCHANGED`), rounded with DWM's border on Windows 11, keeping the owner's caption active (`WM_NCACTIVATE`), and closes on Escape, a pick or deactivation (`CMDPN_CLOSED`), forwarding the palette's notifications to the owner. Prefix providers (`AddProvider`: '@', ':' ...; '?' lists them) supply items the control asks for as needed and keeps, through `CMDPN_GETITEM` or a `pfnGetItem` callback (much faster for long lists: a notification per item pays for every hook on the thread, WTLHelper's dark mode included, and for the popup's forwarding); the text after the prefix goes out with `CMDPN_QUERY`, and `CMDPPF_NOFILTER` providers answer it with their own items. A long list is matched in 25 ms slices on a timer (`CmpSearch`: each step's new results are sorted and merged in, not the whole list again), with a progress line under the box. `Filter` empties the old results before switching lists: they index the old one. Like DiffView it follows WTLHelper's dark mode, and high contrast uses the system colors over the app's (`ForceHighContrast` for testing). MSAA (`CommandPaletteAccessible.cpp`) is a list of the result rows on the list window; the selected row is reported focused while the box has the focus (an active descendant), with focus and selection events as it moves, and the box and the list are named through `IAccPropServices` (which needs COM on the thread). The model is covered by `CommandPaletteTests`; `CommandPaletteDemo` (which links WTLHelper on x64) is for checking by hand.
- `RibbonBar`: a ribbon-lite (`CRibbonBarCtrl`, window class `WC_RibbonBar`), `RIB`-prefixed C-style API (`RIBITEM`, `RIBGROUP`, `RIBTAB`, `RIBCOLORS`, `RIBN_*`; not `RB`, the Rebar's, nor `CRibbon*`, WTL's `atlribbon.h`; internal names are `Rib*`), GDI-drawn. Tabs of labeled groups of items: buttons, toggles, radio items (a tab's items with the same `radio` number), drop-down and split buttons with the app's menu, separators, and the app's own windows (a combo box) made the ribbon's children. Items are by id, which is the command: a click posts `WM_COMMAND` to the owner as a menu would (after `RIBN_EXECUTE`, non-zero: the app ran it), and items sharing an id share their state (`SetItemState`, `EnableItem`, `CheckItem`); `RIBN_UPDATEUI` asks for the selected tab's states before it's painted, and `UpdateUI()` sends it from an app's idle handler. As the window narrows the groups shrink (`src/RibbonBarModel.*`): `RibGroupSteps` takes large items to small three at a time from the right, then small ones to icons, and folds the group last into one button; `RibFitTab` shrinks the lowest `priority` first, a step at a time from the right, round after round, and folds only when none of that priority can shrink; scroll buttons appear when even folded groups don't fit. A surface (`RibSurface` in `src/RibbonBarData.h`) is where a tab's groups are drawn and clicked: the ribbon's own strip, or a `RibPopup` (a folded group opened at its widest, or a tab while the ribbon is minimized, `SetMinimized` or double-clicking a tab). Popups take the activation (a hosted window in one can have the focus) but keep the owner's caption active (`WM_NCACTIVATE`), close on deactivation, Escape or a command run (`HidePopups` marks them, `WM_RIB_CLOSEPOPUPS` destroys them; the click that closed one on its own button doesn't reopen it, `JustClosed`), and hosted windows move into the popup showing their group and back before it's destroyed (`PlaceWindows`); the ribbon and its popups pass the hosted windows' notifications, colors and owner-draw messages to the ribbon's parent. A drop-down opens on the button press: `RIBN_DROPDOWN` (the app may fill the menu or show its own UI), then `TrackPopupMenuEx` owned by the owner (which gets `WM_INITMENUPOPUP`), the click that closed it over the button eaten. Contextual tabs (`AddContext`, `ShowContext`) show after the others in their set's color. The quick access bar (`src/RibbonBarQat.cpp`, `RIBS_NOQAT`) is at the left of the tab row: the user adds commands from the right-click menu and removes them from its button's menu (`RIBN_CONTEXTMENU` lets the app change either, `RIBN_QATCHANGED` follows); `GetState`/`SetState` keep the tab, minimizing and the bar as text (`RibSaveState`). The keyboard (`src/RibbonBarKeys.cpp`): the app's message loop passes messages through `PreTranslateMessage`, so Alt (or F10) shows key tips a level at a time (the tabs and the bar's digits, a tab's commands, a folded group's: `RibAssignKeyTips`, prefix-free) and Alt+a tab's tip goes straight in; each tip is a small window of its own (`RibTipWindow`), as tips drawn on the surface were covered by hosted windows. The arrow keys move a focus (`RibNearest`; Left/Right along the tabs select them, Down goes into the groups, Up back to the tab), Enter runs it, Escape goes back a level (a level's popup closing ends it, so the new level is set before `HidePopups`). The ribbon takes the focus meanwhile and gives it back (`RestoreFocus`, not while a popup has it); a resize or items changing ends it. Tooltips: one tool for each surface's window, moved onto what's under the mouse (disabled items too), the name in bold over `pszTip`; the mouse move that made an item hot reaches the tooltip before the tool moves, so `UpdateTip` relays it again. Like LogView it follows WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message; high contrast uses the system colors over the app's, framing hot and checked states in the highlight color (`ForceHighContrast` for testing). MSAA (`src/RibbonBarAccessible.cpp`): the ribbon's window is a tool bar of the quick access buttons, the tabs (page tabs), the minimize button and the selected tab's commands; each popup is one of its own; the keyboard shortcut is the command's key tips ("Alt, H, B"); default actions are posted (`WM_RIB_ACCACTION`), so a menu's modal loop doesn't run inside the client's call. The model is covered by `RibbonBarTests`; `RibbonBarDemo` (a WordPad-like window, which links WTLHelper on x64) is for checking by hand.
- `Breadcrumb`: a breadcrumb bar, as Explorer's address bar (`CBreadcrumbCtrl`, window class `WC_Breadcrumb`), `BRC`-prefixed C-style API (`BRCITEM`, `BRCBUTTON`, `BRCCOLORS`, `BRCN_*`; commctrl owns `BCM_`/`BCN_`; internal names are `Brc*`), GDI-drawn. The app owns the hierarchy: it gives the segments with `SetPath` (each a text, and a name for the path text, which is the names joined with the first separator; an empty name, "This PC", is left out), and the control only says where the user wants to go (`BRCN_NAVIGATE`, with a source: a segment, a child picked, typed, back/forward, up); the app goes there and calls `SetPath` again. A segment's chevron drops down what's under it, which the app adds with `AddChild` while `BRCN_GETCHILDREN` is sent; the child that is the next segment is bold. When the bar narrows the leftmost segments fold into the root chevron, whose list shows them, deepest first, before the root's children (`BrcLayoutBar` in `src/BreadcrumbModel.*`). The drop-downs are one reused popup (`BrcDropList`, `src/BreadcrumbList.cpp`) that doesn't take the activation: a segment's list takes the mouse capture as a menu does (the mouse moving onto another chevron opens its list; a press dragged onto a row and released picks it; a click elsewhere closes it and is eaten), and the control keeps the focus and passes it the keys. Taking the capture sends a `WM_MOUSEMOVE` where the mouse rests, so a move to the same point isn't one (it opened the list under a resting cursor). Clicking the box's empty part edits the path as text in a real `Edit` (`src/BreadcrumbEdit.cpp`, `ALT_MSG_MAP(1)`; `BRCN_BEGINEDIT` may veto or `SetEditText`); Enter sends `BRCNS_TYPED`, which the app may reject (non-zero) to keep editing; the suggestions (`BRCN_GETSUGGESTIONS`, asked once per parent; the history's paths first) drop down in the same popup without the capture, and the history arrow lists the paths typed before (`GetHistory`/`SetHistory`). The control keeps the back/forward list itself: each `SetPath` records its location (the path text, or the string given), and while `Go` sends `BRCNS_BACKFORWARD` the app's `SetPath` moves along the list instead (`BrcHistory::Replace` if the app writes it differently). The keys (`src/BreadcrumbKeys.cpp`) move a focus frame along the enabled parts (it never takes the focus on a click), Enter runs one, Down opens its list, Left/Right in an open list go to the next one; typing starts editing. `CBreadcrumbShell` (`include/BreadcrumbShell.h`) browses the shell's namespace with it: PIDLs as the segments' `lParam`, the location's parsing name for back/forward, the editing name to edit, `SHParseDisplayName` for typed paths; the app passes it the bar's `WM_NOTIFY`. `IShellFolder::CompareIDs` isn't a consistent order, and `std::sort` with it ran past the array (a crash) and took minutes on Gallery: non-file-system folders go through `SafeSort` (a bounded merge sort), file system ones by name. Like LogView it follows WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message; high contrast uses the system colors over the app's, framing hot and pressed parts in the highlight color (`ForceHighContrast` for testing). Tooltips: one tool moved onto the hot part, naming where Back, Forward and Up go (`SetString` replaces the words). MSAA (`src/BreadcrumbAccessible.cpp`): the bar is a tool bar named "Address: <location>" whose children are its parts (each segment a push button and a drop-down button); an open list is a list whose selected row is reported focused (the control keeps the real focus); default actions are posted (`WM_BRC_ACCACTION`). The model is covered by `BreadcrumbTests`; `BreadcrumbDemo` (a folder browser over the file system, the registry or the shell's namespace, which links WTLHelper on x64) is for checking by hand.
- `Notify`: notifications that don't stop the user, on one message model (`src/NotifyModel.*`), `NTF`-prefixed C-style API (`NTFMESSAGE`, `NTFBUTTON`, `NTFCOLORS`, `NTFN_*`; internal names are `Ntf*`), GDI-drawn. A message has a severity (WinUI InfoBar's colors, light and dark, and a Segoe Fluent Icons glyph, else Segoe MDL2 Assets, checked by `GetTextFace`), a title, a text with links parsed from a little markup (`<a id="x">here</a>`, `href` when there's no id, `&lt;` and the like; anything malformed stays text), buttons, a close button, and optionally details the user shows (a link at the text's end, `NtfDetailsLink`), a progress bar (a value, or a sweeping segment) and a "don't show again" checkbox whose state goes with `NTFN_CLOSED`. `NtfWrap` wraps the runs with their links' places; `NtfLayoutMessage` lays a message out as an info bar's row (the title in bold before the text, the buttons beside it when it keeps `minText`, else under it) or a toast (the title on its own line, the buttons under the text at the right). `src/NotifyPaint.cpp` draws and hit-tests a message for both. `CInfoBarCtrl` (`WC_InfoBar`) is a strip of rows, the newest on top, in their severities' colors; past `SetMaxRows` the rest fold into an "N more" strip that shows them all ("Show fewer"). Rows slide in and out (as Windows' animation setting says, or `NTFS_NOANIMATION`/`NTFS_ALWAYSANIMATE`) and the control sends `NTFN_HEIGHTCHANGED` every frame, so the window's layout follows. A button click sends `NTFN_BUTTONCLICK` and the message closes unless the app returns non-zero; `NTFN_CLOSED` is only the user's. Its keys: Tab and the arrows go along the rows' parts (`WM_GETDLGCODE` asks for Tab only while there's a next part), Enter presses, Delete closes, Ctrl+C copies the message. `CToastHost` (not a window: `Attach` to a window, `Detach` in its `WM_DESTROY`) shows messages as toasts in a corner of the window's client area: layered popups owned by its top-level window, `WS_EX_NOACTIVATE`, rounded by DWM on Windows 11; the newest in the corner, those that don't fit (or past `SetMaxShown`) waiting with their clocks stopped (`NtfPlaceToasts`); they fade, slide, glide to new places, follow the window through a WinEvent hook on its location changes (no subclassing), and close when their `timeout` runs out (`NTFR_TIMEOUT`); the mouse over any toast, or a toast having the keys, stops every clock. A toast paints as soon as it shows (`UpdateWindow`): one moved before its first paint stayed blank in dark mode. Its notifications go to the window (`hwndFrom` the toast, `idFrom` the host's id); a click on a toast's body is `NTFN_BUTTONCLICK` with the button 0. `Focus` (an app's shortcut) gives the keys to the newest toast (Tab along its parts, Up/Down to the next toast, Escape gives them back; `SetActiveWindow` works on a `WS_EX_NOACTIVATE` window, and the owner's caption is kept active with `WM_NCACTIVATE`). Like DiffView they follow WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message; high contrast uses the system colors over the app's, framing hot parts in the highlight color (`ForceHighContrast` for testing). Tooltips: the close buttons and links that are addresses. MSAA (`src/NotifyAccessible.cpp`, one `IAccessible` over an `NtfAccSource` each window implements): the info bar is a grouping whose children are each row's message (an alert, named by its title, described by its text) followed by its parts; a toast is an alert with its parts as children; a new message raises `EVENT_SYSTEM_ALERT` (always: screen readers listen for it before asking for the object); default actions are posted (`WM_USER + 120`). The model is covered by `NotifyTests`; `NotifyDemo` (which links WTLHelper on x64) is for checking by hand.
- `Gantt`: a Gantt chart (`CGanttCtrl`, window class `WC_Gantt`), `GNT`-prefixed C-style API (`GNTTASK`, `GNTCOLORS`, `GNTN_*`; internal names are `Gnt*`), GDI-drawn: a grid of the task tree with columns (`SetColumns`: name, start, finish, duration, % done) left of a splitter, and the bars on a calendar at the right under a two-tier header whose units follow the zoom (`GntPickUnits`: hours to years; Ctrl+wheel zooms around the mouse, Shift+wheel pans). The model (`src/GanttModel.*`) is window-free: times are minutes since 1601 (`GntTime`, local, no time zones), a task's `duration` is working minutes (0: a milestone) and its finish comes from the calendar (`GntCalendar`: working days as weekday bits, working hours, holidays; `AddWork`, `WorkBetween`), summaries take their dates and work-weighted progress from their children (`Recompute`), and links are the four kinds with a lag. `CanLink` refuses summaries, duplicates either way and cycles. `PushSuccessors` moves the tasks after a moved one later (never earlier) and `Schedule` (`Reschedule()`) does the whole project in topological order. The user drags a bar (move), its ends (start, finish), its progress handle, or from its link handle (shown on the hot bar) to another bar; the task changes live (its summaries and the grid follow), snapped to the day or, at the hours zoom, the hour; on the drop `GNTN_TASKCHANGING` (`NMGANTTCHANGE`; non-zero vetoes and puts the project back, or the app changes the values) then the push (unless `GNTS_NOAUTOSCHEDULE`) and `GNTN_TASKCHANGED`; linking is `GNTN_LINKADDING`/`GNTN_LINKADDED`; Escape or a lost capture cancels. Undo (`GntHistory`, Ctrl+Z/Ctrl+Y, `GNTN_RESTORED`) keeps whole projects, so the API's changes to tasks, links or the calendar clear it. The keys (`src/GanttKeys.cpp`): the arrows select and expand, Alt+Left/Right move the selected task a working day or an hour (Shift: its finish) through the same veto and undo (`Apply`), F2 renames in place (an `Edit` in `ALT_MSG_MAP(1)`, `m_Edit(this, 1)`: without the object any message to it crashes, Shift+Alt's input language change included; `GNTN_RENAMING` can refuse), Delete removes the link clicked (`LinkAt` by `GntLinkDistance`; `GNTN_LINKREMOVING`). `GNTS_READONLY` turns all of it off. Markers (`AddMarker`) are dotted lines with a tag (`GNTN_MARKERCLICK`). Tooltips: one tool moved onto the bar, link or marker under the mouse. Like DiffView it follows WTLHelper's dark mode through `GetSysColor` and the registered `ThemeChanged` message; high contrast uses the system colors over the app's (and the tasks' own colors), with no shades between them (`GntDraw::Shade`), the time off hatched and the selected row in the highlight colors (`ForceHighContrast` for testing). MSAA (`src/GanttAccessible.cpp`) is an outline of the rows shown on the control itself: each item named by its task, its level as the value, described by its dates, duration, progress and the links into it; a summary's default action expands it, a task's is a double click (posted, `WM_GNT_ACCACTION`); selection, focus, reorder, name and description changes are reported once a client has asked. The model is covered by `GanttTests`; `GanttDemo` (a website relaunch plan, which links WTLHelper on x64) is for checking by hand.
- `MarkdownViewLib`: `CMarkdownView`, a WTL wrapper around a Direct2D markdown viewer/editor ("Tinta"). Message handlers are thin pass-throughs to free `handleXxx(App&)` functions. Keep logic in those functions and not in the window class.
